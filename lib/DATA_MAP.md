### 🛠 Operational Rules for `records`:
1. **The ID Duality Law**: The Brain MUST distinguish between the **System ID** (`Id`) and the **Business UUID** (`record_id`).
   - Use `Id` (Integer) strictly for REST URL segments (PATCH/DELETE).
   - Use `record_id` (UUID) for internal data logic and the `fields` payload.
2. **REST URL segment**: Prefer `.../api/v3/data/{baseId}/{tableUid}/records/{id}` for PATCH/DELETE; some Noco builds use `.../{tableUid}/{id}` without `/records/`. The Brain tries both. The **wrapper `id`** (System Integer) usually goes in the last segment; the Brain may also try the business UUID as the path segment if the server expects it.
3. **Sacred Singleton Law**: Before starting a new record, the Brain MUST stop open intervals for **projected today** (profile wall-clock day of `start_time`), then optionally merge **at most one** oldest **pre-today** open row (multi-day `running` handoff) — not a mass scan of all history. PATCH those to `stopped`, then POST the new row. Prefer **one multi-row bulk PATCH** per chunk (same `fields` shape as rule 6); then **per-row** fallback if bulk fails or a row has a non-bulk PK shape.
4. **Clean Slate**: `date_key` and `is_manual` are strictly banned.
5. **PATCH 404 recovery**: If `PATCH .../records/{Id}` returns 404 but the row still exists, the Brain re-queries by `record_id` (UUID) and retries once with the server’s wrapper **Id** (and may include numeric `id` in the JSON body). Stale cache PKs must not block stop.
6. **Bulk PATCH (preferred)**: On many v3 hosts, single-row `PATCH .../records/{id}` returns 404; the Brain therefore tries **bulk** `PATCH` to `.../{tableUid}/records` with `[{"id":<wrapper Id>,"fields":{...}}]` **first**, then falls back to per-row URLs if needed.
7. **Bulk DELETE (preferred)**: Same pattern — **bulk** `DELETE` to `.../{tableUid}/records` with body `[{"id":<wrapper Id>}]` first, then per-row `DELETE` URLs if needed.
8. **Timeline day bucket**: Rows are grouped into a calendar day using **profile wall-clock** (`start_time` UTC + profile offset), **not** the raw UTC `YYYY-MM-DD` prefix of `start_time`. Otherwise same-local-day sessions can disappear from “today.”
9. **Optimistic timeline UI**: The Brain may merge **in-memory-only** overlays into the timeline/active row **before** HTTP completes: synthetic “stopped” end times, synthetic “deleted” (row hidden), and a **pending** running row while a primary `POST` is in flight. Overlays are cleared when the server round-trip succeeds, **reverted** on failure (`clearOptimisticTimelineUi`), or on sign-out. `stopRecordByDocId` / `deleteRecordByDocId` return `bool` so the Shell can show **SnackBar + Try again**.
10. **Stats day scope**: Durations for the Stats view use **`timezone_offset`** (numeric) with `utcRangeForWallClockDate` for the **selected timeline day** — the same wall-clock basis as the list — not the string `preferred_timezone` label alone. The aggregated-stats cache key includes **per-record** ids/times so switching days cannot reuse another day’s tree.



## 2. Table: `categories`
**Business PK:** `category_id` (string, data) | **System PK (envelope):** `Id` (Integer) — **THE BULK-ONLY MANDATE** (this project / host): **never** put `Id` or `category_id` in the URL path for PATCH or DELETE.

| **Id** | Integer | **Bulk envelope `id`** | **YES** | Noco list-item id. **PATCH/DELETE**: send as **`"id": <int>`** on each array element; URL stays **`.../data/{base}/mhg7mv6dfsgq9i0/records`** only. |
| **category_id** | String | **Data / FK** | **YES** (for normal rows) | Unique slug/UUID (`life`, etc.). Inside **`fields`** only. |
| **user_id** | String (UUID) | **FK (Profile)** | **YES** | Owner of the category. |

| **parent_id** | String | **FK (Category)** | NO | Link to a parent `category_id`. |

### 🛠 Operational Rules for `categories`:
1. **Relationship:** The `category_id` here must match the `category_id` used in the **Records** table.
2. **UI Rendering:** Prioritize `color_value` and `icon_code_point` for the Flutter UI.
3. **Data Parsing:** Ensure integer fields are not treated as doubles/strings during JSON conversion.
4. **THE BULK-ONLY MANDATE:** **PATCH** = `PATCH .../mhg7mv6dfsgq9i0/records` with body **`[{"id": <Integer Id>, "fields": {...}}]`**. **DELETE** = `DELETE` the same collection URL with body **`[{"id": <Integer Id>}]`**. No `/records/35`, no `/records/etnika` — those 404 on constrained hosts.
5. **ID duality (same as records):** Use **`id`** in the JSON array element (integer system `Id`) to identify the row; use **`category_id`**, **`user_id`**, **`name`**, **`parent_id`**, etc. only inside **`fields`**.
6. **POST (create):** Still **`POST .../records`** with `{"fields": {...}}` (or bulk array), including a client-generated **`category_id`** so rows are not ghosts. Set **`order`** to the next free integer among siblings (e.g. `max(order)+1`).
7. **Reorder:** Use debounced **bulk** `PATCH .../records` with `[{"id":<int>,"fields":{"user_id":...,"category_id":...,"order":<int>}}]` — same pattern as plans `@DATA_MAP` **`order`** (dense 0…n−1 after a drag session).

| **title** | String | Data | **YES** | The name or description of the task/plan. |

| **end_time** | ISO8601 String | Time | NO | Scheduled deadline/finish time. |
| **order** | Integer | UI | **YES** | Manual sorting index (default: `0`). |
| **parent_plan_id**| String | Hierarchy | NO | Link to another `plan_id` for sub-tasks. |
| **checklist** | JSON String | Complex | **YES** | Array of sub-items (default: `[]`). |
| **order** | Integer | UI | **YES** | Manual sorting index (default: `0`). |
| **note** | String | Text | NO | Personal notes or extra details. |
| **tag** | String | Metadata | NO | Extra label for filtering/grouping. |

### **Operational Logic for Revision:**

1. **The `order` Field (Priority):**
   * Even though your CSV shows `0` for everything, this field is critical for the UI. It allows the user to drag and drop plans.
   * **Rule:** When a new plan is created, it should take the next available integer (e.g., `max(order) + 1`).
2. **`is_done` (Boolean vs String):**
   * Unlike the `records` table which has multiple statuses (`running`, `stopped`), plans are binary.
   * **Rule:** If `is_done` is `true`, the UI should likely strike through the text or move it to a "Completed" list.
3. **Time Interpretation:**
   * These timestamps represent **intent**, not actual work duration. 
   * **Rule:** When converting a "Plan" into a "Record", `plan.start_time` can be used as a suggestion, but the `record.start_time` should be the actual moment the user hits "Start".
4. **Hierarchical Plans:**
   * The `parent_plan_id` allows for nested task lists. If this field is filled, the plan is a "sub-plan."
5. **REST Construction**: Plans MUST use the **Integer Id** for `PATCH` and `DELETE` URL paths. Do not use the `plan_id` UUID in the URL.



### **Table Specification: `profiles`
**Business PK:** `user_id` | **System PK (REST):** `Id` (Integer)

| Field (Column) | Type | Role | Required | Description / Notes |
| :--- | :--- | :--- | :--- | :--- |
| **Id** | Integer | **REST URL PK** | **YES** | System-generated index. REQUIRED for row URL. |
| **user_id** | String (UUID) | **PK** | **YES** | Unique ID for the user. Matches `user_id` in all other tables. |
| **email** | String | Data | **YES** | Primary contact and login identifier. |
| **password** | String | Security | **YES** | Hashed password string. |
| **name** | String | Data | NO | Full name (optional). |
| **display_name** | String | Data | **YES** | The nickname shown in the app (e.g., "Nikita"). |
| **avatar_url** | String | UI | NO | URL to the profile image. |
| **updated_at** | ISO8601 String | System | NO | Automatically updated timestamp of the last change. |
| **primary_language**| String | UI | **YES** | App interface language code (e.g., "ru", "en"). |
| **theme_mode** | String | UI | **YES** | App appearance: `light`, `dark`, or `system`. |
| **preferred_timezone**| String | Time | **YES** | Textual timezone name (e.g., "New York (UTC-5)"). |
| **timezone_offset** | Integer | Time | **YES** | Numerical offset from UTC (e.g., -5). |
| **biometric_enabled**| Boolean | Security | **YES** | Toggle for FaceID/Fingerprint authentication. |

### **Operational Logic for Revision:**

1. **The Role of `user_id`:**
   * This is the "Master Key". Every single row in `records`, `categories`, and `plans` must have a `user_id` that matches this one to ensure users only see their own data.
2. **Timezone Handling:**
   * **Preferred Timezone:** Used for display (showing the user which city/zone they selected).
   * **Timezone Offset:** Used for calculations. When the app saves a `start_time`, it uses this offset to ensure the time is stored correctly in UTC.
3. **PATCH vs. Full Update:**
   * If the user only changes their `theme_mode`, the app should send a **PATCH** request containing only that field. You do **not** need to send the email or password again.
4. **Extensibility:**
   * If you decide to add a new setting (e.g., `notifications_on`), you simply add a new column to this table. The existing code for `display_name` or `email` will not break because the API only touches the fields you explicitly tell it to.
